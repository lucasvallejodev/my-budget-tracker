# Prisma to Drizzle migration

## Plan

- [x] Inventory schema, queries, actions, deployment and environment configuration.
- [x] Recreate the five existing PostgreSQL tables and enums in Drizzle, preserving physical names/types/constraints.
- [x] Replace the client with a pooled direct PostgreSQL connection.
- [x] Migrate reads, account/payee creation, transaction creation and soft deletion.
- [x] Generate SQL and provide distinct fresh-database and existing-database setup paths.
- [x] Exercise real SQL in an isolated PostgreSQL test runtime, including rollback and ownership.
- [x] Remove Prisma packages, generated client, schema/config and Docker steps.
- [x] Run lint, tests, type checking and production build.
- [x] Add local PostgreSQL Docker Compose configuration as requested during migration.
- [ ] Start Docker PostgreSQL and apply/verify migrations there — Docker is not installed on this machine.

## Compatibility decisions

Keep the quoted table names `Account`, `Payee`, `Transaction`, `MonthlyHistory`, and `MonthlyCategoryGroupHistory`. IDs remain text (UUIDs generated by the application), amounts remain double precision, and timestamps remain without time zone at millisecond precision. Changing money storage to decimal is a separate data migration.

The original environment used a Prisma proxy URL. The user then requested local PostgreSQL through Docker Compose. `.env` now targets the local database with a generated password; credentials were not printed. No data was copied from the hosted database, and no hosted database was changed.

Do not apply the initial CREATE TABLE migration blindly to an existing database. Verify its schema and baseline it first. No existing rows need to be copied or deleted for this ORM migration.

- 30 tests pass, including 10 new PostgreSQL integration tests using the generated SQL migration in PGlite.
- Integration coverage: defaults/IDs/timestamps, ownership, active-row filters, monthly income/expense upserts, optional payees, unique constraints, create rollback after a later failure, deletion rollback, double-deletion protection, transfer guard, schema-drift detection and invalid connection URL handling.

## Delivered files and behavior

- `src/db/schema.ts`: five tables, two enums, relations and inferred row types; original text IDs, timestamp precision, float types, index and foreign-key names retained.
- `src/db/index.ts`: lazy, cached node-postgres pool. Importing server modules during builds does not connect to a database. Connection URL validation never prints credentials.
- `src/db/repository.ts`: shared data access used by all APIs, server actions and account detail lookup.
- `drizzle/0000_initial.sql` and `drizzle/meta`: generated initial migration and versioned schema snapshot.
- `drizzle.config.ts`: Drizzle Kit configuration.
- `scripts/database.mjs`: read-only schema verification and guarded initial-baseline workflow for a matching existing database. Baseline changes only the migration journal, not application data. It refuses incompatible schemas/history.
- `docker-compose.yml`: PostgreSQL 17, persistent volume, readiness check, localhost-only database port; optional app container under the `app` profile.
- `Dockerfile`: Node 22 build with no code generation or Prisma engine copies; public Clerk build arguments retained.
- `.dockerignore`: prevents local secrets and build artifacts from entering images.
- `README.md` and `.env.example`: updated setup guide and PostgreSQL environment examples. The pre-existing `.gitignore` edits were left intact.

## Financial consistency corrections made during migration

Creation and deletion now use database transactions, account/row locking, and SQL arithmetic. Soft deletion reverses the account balance and both monthly histories exactly once. Missing legacy aggregate history aborts deletion instead of leaving partial updates. Paired transfer deletion is explicitly rejected because there is no paired-transfer editing flow in this project. Account/payee ownership is validated before a transaction is created, empty optional payee IDs become NULL, and read lists exclude soft-deleted rows.

## Remaining local startup steps

After installing and starting Docker Desktop:

```sh
npm run db:up
npm run db:migrate
npm run db:check
npm run dev
```

The new local database starts empty. Existing hosted records require a separate export/import if wanted. The Compose volume persists across normal stops; neither schema migration nor application startup deletes it.

Reference documentation used: [Drizzle PostgreSQL setup](https://orm.drizzle.team/docs/get-started/postgresql-existing), [transactions](https://orm.drizzle.team/docs/transactions), and [upserts](https://orm.drizzle.team/docs/guides/upsert). Implementation targets the installed stable Drizzle ORM 0.45.2 / Kit 0.31.10 APIs.
